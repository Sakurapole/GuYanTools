# AI 图像处理工具平台功能需求文档

## 1. 文档标题

AI 图像处理工具平台功能需求文档

版本：0.1（需求草案）  
日期：2026-10-04  
适用产品：GuYanTools 桌面端及其模型插件运行时

## 2. 背景与概述

当前插件名称和页面都围绕“图像超分”和 Real-CUGAN 设计，但实际目标已经扩大为一个可扩展的 AI 图像处理工具。用户需要在同一工作台中完成图像放大、降噪、去模糊、修复、补全、抠图、风格处理和 AI 生成，并可以在本机模型与第三方远程模型之间切换。

仓库已经有模型插件运行时的基础能力：插件 manifest 可声明模型运行时，宿主提供 Python/Conda 环境、依赖安装、文件句柄、任务、取消和插件权限控制；当前 `ModelRuntimeApi` 仍只表达 CPU/CUDA、单图输入、权重文件和一次推理。现有 `docs/desktop/MODEL_PLUGIN_RUNTIME.md` 是 Real-CUGAN 首期基线，不代表本平台已经支持本文档中的多模型、多后端和远程生成能力。

本需求将产品定义为“AI 图像处理工具平台”：宿主负责通用的插件生命周期、权限、文件、任务、环境和资源管理；每一个模型或模型族通过插件声明任务类型、模型元数据、参数、输入输出契约和后端适配。模型加载、推理编排、预处理和后处理不写死在宿主中。

## 3. 目标

- 在一个工作台中发现并使用多类 AI 图像处理模型。
- 保留并兼容当前 Real-CUGAN 单图超分流程，迁移后不改变其已验证的安全边界。
- 支持本地 CPU、CUDA、TensorRT、ONNX Runtime Execution Provider、WebGPU 等运行方式，并在运行前展示真实可用性。
- 支持第三方远程图像生成或编辑模型，同时隔离 API 密钥、网络权限、费用和数据发送范围。
- 让新增模型主要通过插件 manifest、插件 UI 和插件 worker 完成，减少宿主改动。
- 让任务可取消、可重试、可恢复、可追踪，并在离开页面后继续显示历史状态。
- 使用 GuYanTools 自定义组件库保持桌面工作台一致的视觉、键盘和无障碍体验。

## 4. 非目标

- 第一阶段不承诺训练模型、微调模型、数据集管理或标注工具。
- 不把任意第三方插件自动提升为可执行本机代码的可信模型插件。
- 不在宿主中内置所有模型的业务逻辑或模型专用参数。
- 不默认实现视频生成、视频超分和长视频队列；这些能力需要独立的媒体任务需求。
- 不承诺所有机器都能使用 CUDA、TensorRT 或 WebGPU；页面必须根据探测结果禁用或解释不可用后端。
- 不把远程 provider 的能力、模型名称、价格或可用性硬编码成宿主永久契约。

## 5. 用户与角色

| 角色 | 目标 | 权限与限制 |
| --- | --- | --- |
| 本地图像处理用户 | 选择图片、模型、后端和参数，运行并导出结果 | 可使用已启用且有权限的内置/签名插件；不能读取未授权路径 |
| 高级本地用户 | 管理 Python/Conda 环境、模型权重、TensorRT engine 和缓存 | 可删除或重建插件专用环境；危险操作需要明确确认 |
| 远程模型用户 | 调用第三方生成/编辑 provider | 只能使用用户主动配置的 provider、密钥和额度；网络发送前必须显示范围 |
| 插件开发者 | 发布模型插件和自定义参数界面 | 只能通过 manifest、SDK 和已批准 capability 访问宿主能力 |
| 平台维护者 | 审核插件、签名、后端适配和兼容性 | 维护官方信任根、模型目录、后端版本矩阵和撤销状态 |

## 6. 范围

### 6.1 范围内

- AI 图像处理工作台及固定左右侧栏布局。
- 模型目录、任务类型筛选、模型详情、版本和许可信息。
- 本地模型插件、远程 provider 插件和混合插件。
- Real-CUGAN、图像还原、修复、生成、编辑等模型族的统一任务协议。
- CPU、CUDA、TensorRT、ONNX Runtime EP、WebGPU 后端声明、探测、选择和失败回退。
- 单图和可扩展的多输入图像任务；首期实现范围由每个插件的 manifest 声明。
- 输入预览、参数表单、遮罩/参考图、前后对比、缩放和导出。
- 任务队列、取消、重试、历史、日志、错误和资源占用状态。
- 本地权重导入、受控下载、校验、缓存和清理。
- API 密钥安全存储、远程请求确认、隐私提示、使用量和费用元数据。
- 插件 UI 对 `@guyantools/plugin-ui` 的使用和自定义 token/公开 `::part(...)` 样式覆盖。

### 6.2 范围外

- 任意模型的自动发现和未经审核的代码执行。
- 账号体系、云端任务同步和跨设备模型缓存。
- 模型训练、LoRA 训练、数据集标注和版本控制。
- 专业色彩管理工作流（如完整 ICC 编辑链）；仅要求保留常见色彩信息并避免静默破坏。

## 7. 用户场景与流程

### 7.1 本地处理主流程

1. 用户打开“AI 图像处理工具”，中央工作区显示输入预览、任务类型和最近任务，左侧显示工具/任务导航，右侧显示模型与参数。
2. 用户导入一张或多张图片，系统生成临时文件句柄并显示文件名、格式、尺寸、色彩空间和透明通道状态。
3. 用户选择任务类型，例如“超分辨率”“图像还原”“图像修复”或“图像生成/编辑”。
4. 系统列出支持该任务和当前输入格式的模型插件，展示模型版本、来源、许可、预计资源和可用后端。
5. 用户选择模型和运行后端。默认选项为“自动选择”，系统按可用性、模型兼容性和用户偏好排序。
6. 系统探测运行环境、权重、依赖、驱动、后端版本和显存，必要时引导安装或导入依赖。
7. 用户配置模型参数；表单必须由模型 manifest 的参数 schema 驱动，并根据前置条件动态显示/隐藏字段。
8. 用户点击“开始处理”。系统创建可追踪任务，显示阶段、进度、取消入口和资源状态。
9. 任务完成后，中央区域显示原图/结果对比；用户可以预览、复制结果、导出、重新处理或从结果继续下一个操作。
10. 任务记录进入历史列表，包含模型、版本、后端、参数摘要、耗时、输出和错误信息。

### 7.2 远程生成或编辑流程

1. 用户选择标记为“远程 provider”的模型。
2. 页面显示数据发送范围、provider、区域、保留策略、预计费用（若 provider 提供）和所需密钥状态。
3. 用户确认后，插件从 secrets 服务取得密钥，不能把密钥传给 renderer、日志或任务输入明文。
4. 插件将 prompt、参考图、遮罩和模型参数转换为 provider 请求；宿主只提供受限网络请求和文件授权。
5. 系统显示排队、上传、远程处理、下载和后处理阶段。可取消的阶段必须真实取消或明确标记为“等待 provider 完成”。
6. 返回结果后，用户可以查看 provider、模型、提示词摘要和生成参数，并选择是否保存完整提示词。

### 7.3 后端不可用替代流程

- 当 TensorRT engine 与当前 GPU/驱动/模型版本不匹配时，系统应说明原因，并允许回退到 CUDA 或 CPU；不得静默改变后端。
- 当 WebGPU 不可用、设备丢失或浏览器渲染器内存不足时，系统应提供本地可用后端和重试入口。
- 当 ONNX 模型不支持目标 Execution Provider 的算子时，系统应展示不兼容算子/阶段摘要，并允许选择其他 EP。

### 7.4 失败流程

- 输入损坏、格式不支持、尺寸超过限制、模型权重校验失败、依赖安装失败、权限不足、网络超时、额度不足、进程崩溃和输出写入失败都必须产生可读错误码与操作建议。
- 取消任务后，系统必须停止可停止的本地进程、释放临时句柄、保留取消记录，并禁止同一任务重复写入输出。
- 应用关闭或插件停用时，本地运行进程进入终止流程；无法立即终止时记录残留进程检查结果。

## 8. 功能需求

### 8.1 工作台与导航

- `FR-1`：系统复用宿主顶栏，插件不重复绘制顶栏、面包屑或产品介绍；插件提供固定左侧任务导航栏、中央可滚动工作区和固定右侧模型/参数栏，中央内容不得被左右栏遮挡。
- `FR-2`：左右栏应支持收起、恢复和状态持久化；窗口宽度不足时必须采用结构化折叠或抽屉，不得通过缩放字体解决溢出。
- `FR-3`：用户应能从左侧导航在“工作台、模型库、任务历史、运行环境、设置”之间切换，切换不应丢失未提交参数。
- `FR-4`：页面应提供全局搜索，至少可搜索模型名称、任务类型、插件、任务 ID 和输出文件名。
- `FR-5`：所有交互控件必须支持键盘焦点、可读名称、禁用和加载状态；状态不能只通过颜色表达。

### 8.2 模型目录与插件发现

- `FR-6`：系统应按任务类型、输入格式、运行位置（本地/远程）、后端和许可筛选模型。
- `FR-7`：模型卡片应展示插件 ID、模型 ID、版本、作者/来源、许可、支持任务、输入输出格式、权重大小、预计显存/内存和可用后端。
- `FR-8`：系统应区分“已安装、可下载、需要配置、不可用、已撤销、版本过期”状态。
- `FR-9`：插件 manifest 应声明模型能力，但 `capabilities` 不得隐式授予宿主权限；执行本机模型仍需显式 `models.execute` 和可信来源校验。
- `FR-10`：模型目录应支持模型版本固定、更新提示、回滚到已缓存版本和完整性校验。

### 8.3 统一模型插件契约

- `FR-11`：每个模型插件应声明一个或多个 `task`，至少支持 `upscale`、`restore`、`denoise`、`deblur`、`inpaint`、`outpaint`、`generate`、`edit`、`segment` 中的一个。
- `FR-12`：插件应声明输入端口和输出端口，包括媒体类型、格式、是否支持 alpha、尺寸限制、颜色空间和是否允许多图/遮罩/文字提示。
- `FR-13`：插件应通过参数 schema 声明字段类型、默认值、范围、枚举、单位、依赖条件、敏感性和是否影响可复现性；宿主 UI 不得猜测模型参数。
- `FR-14`：插件应声明预处理、推理、后处理阶段及其进度权重，任务系统据此显示阶段进度。
- `FR-15`：插件应声明模型权重来源、下载 URL、SHA-256、文件许可、上游 commit/版本和安全加载方式。
- `FR-16`：插件应声明支持的运行后端及后端特定依赖、最低驱动/运行时版本、精度（FP32/FP16/INT8）和已知限制。
- `FR-17`：插件应声明结果元数据策略，包括是否保存模型、版本、参数、随机种子、provider 和输入摘要。

### 8.4 本地运行后端

- `FR-18`：系统应支持通用 `backend` 标识，至少包括 `cpu`、`cuda`、`tensorrt`、`onnxruntime`、`webgpu`；具体插件可声明子类型和版本约束。
- `FR-19`：系统应在任务开始前返回后端探测结果：可用性、设备名称、驱动/运行时版本、显存或共享内存、精度支持和失败原因。
- `FR-20`：自动后端选择必须按照插件声明的兼容性、用户偏好、设备可用性和性能排序，并在 UI 中显示最终选择及原因。
- `FR-21`：用户手动指定后端时，系统不得静默回退；若允许回退，必须先提示并记录用户确认。
- `FR-22`：CPU 后端应提供无需专用 GPU 的兼容路径，并限制并发和内存以避免桌面被拖垮。
- `FR-23`：CUDA 后端应校验 NVIDIA 驱动、CUDA/PyTorch 依赖、设备能力、显存和 FP16 支持；安装 CUDA wheel 不得被视为设备可用。
- `FR-24`：TensorRT 后端应支持 engine 构建或导入、engine 与模型/设备/驱动/精度的兼容校验、构建缓存、缓存失效和重新构建；构建过程必须是可取消任务。
- `FR-25`：ONNX Runtime 后端应支持 Execution Provider 选择和优先级，并能报告模型算子无法由目标 EP 执行的情况。
- `FR-26`：WebGPU 后端应在渲染器/受控 worker 中运行，明确浏览器 GPU adapter、设备丢失、共享内存和跨平台差异；不得假设 Node/Electron 主进程可直接使用 WebGPU。
- `FR-27`：后端适配应允许后续接入 DirectML、OpenVINO、ROCm、CoreML、NNAPI 等，但未验证的后端不得显示为“已支持”。

### 8.5 Real-CUGAN 兼容

- `FR-28`：系统应保留 Real-CUGAN 作为内置模型插件，支持当前已声明的 2x/3x/4x、tile、CPU/CUDA 和半精度约束。
- `FR-29`：Real-CUGAN 的模型参数、权重来源、上游许可证和安全权重加载方式必须迁移为 manifest/插件元数据，不得复制到宿主通用逻辑。
- `FR-30`：Real-CUGAN 现有输入句柄、输出目录句柄、任务取消和结果文件名行为必须保持兼容；旧任务记录仍可查看。
- `FR-31`：Real-CUGAN 不支持的后端应显示为不支持或通过插件提供明确的 ONNX/TensorRT 转换版本，不得将 PyTorch 权重直接当作 TensorRT/ONNX 模型。

### 8.6 还原、修复与编辑

- `FR-32`：系统应支持模型声明的任务类型：去噪、去模糊、去压缩伪影、划痕/旧照片修复、低照度增强、色彩修复、超分、抠图、局部修复和扩图。
- `FR-33`：局部修复和扩图应支持遮罩、参考图、画布边界和遮罩可视化；遮罩坐标必须与原图/预览缩放保持一致。
- `FR-34`：用户应能在处理前后切换原图、结果、差异图和并排/滑块对比；对比组件必须支持缩放、适应窗口和透明棋盘格。
- `FR-35`：处理失败时不得覆盖原图；输出应先写入临时文件，校验成功后再原子移动到目标目录。

### 8.7 第三方大模型生成与编辑

- `FR-36`：系统应支持远程 provider 插件，provider 负责 API 版本、模型名、请求体、流式响应和结果解析，宿主只提供受限网络、密钥和文件授权。
- `FR-37`：生成任务至少应支持 prompt、negative prompt（若 provider 支持）、尺寸、数量、随机种子、质量/步数、参考图和遮罩等模型声明参数。
- `FR-38`：远程请求前必须展示发送的数据类型和目的地；用户未确认时不得上传本地图片或调用付费接口。
- `FR-39`：API 密钥只能通过 secrets 服务读写，日志、任务输入、错误详情和 renderer 状态不得包含明文密钥。
- `FR-40`：provider 应返回请求 ID、模型标识、耗时、计费/额度元数据（若可用）和结果来源；失败需区分鉴权、额度、限流、网络、内容政策和 provider 错误。
- `FR-41`：系统应支持 provider 超时、重试策略和幂等键；不可重试的内容政策错误不得自动重试。
- `FR-42`：远程生成结果应标记来源和生成元数据；用户可选择保存完整 prompt、仅保存摘要或不保存 prompt。

### 8.8 文件、权重与缓存

- `FR-43`：插件只能通过临时文件句柄或 FileGrant 访问用户选定的文件和目录，不得获得任意本机路径。
- `FR-44`：系统应校验输入 MIME、真实文件类型、文件大小、像素尺寸和解码结果；扩展名不能作为唯一校验依据。
- `FR-45`：系统应支持 PNG、JPEG、WebP、BMP，其他格式由插件声明；alpha、EXIF、方向和色彩信息必须在任务详情中可见。
- `FR-46`：权重下载必须支持来源白名单、HTTPS、SHA-256 校验、断点续传/取消、磁盘空间检查和清理。
- `FR-47`：TensorRT engine、ONNX 转换结果和模型缓存必须按插件、模型版本、设备、驱动、后端和精度隔离，不能错误复用。
- `FR-48`：用户应能查看缓存占用、删除未使用缓存并在删除前看到受影响的模型/任务。

### 8.9 任务、历史和观测

- `FR-49`：每个任务应有唯一 ID、插件 ID、模型版本、后端、参数摘要、输入摘要、创建时间、状态、阶段进度、输出和错误。
- `FR-50`：任务状态至少包括 `queued`、`preparing`、`uploading`、`running`、`postprocessing`、`completed`、`failed`、`cancelled`、`blocked`。
- `FR-51`：任务应支持取消、重试、复制参数重新运行、打开输出目录和删除历史记录；重试必须引用原任务且不覆盖原结果。
- `FR-52`：任务事件应有节流和序列号，乱序或重复事件不能使 UI 回退到旧状态。
- `FR-53`：日志分为用户可读摘要和诊断详情；详情可导出，默认不包含密钥、完整图片内容或未授权路径。
- `FR-54`：系统应记录后端探测、模型加载、engine 构建、依赖安装、网络请求结果和进程退出原因，支持按任务 ID 关联。

### 8.10 权限、信任与安全

- `FR-55`：`models.execute`、`network.fetch`、`files`、`downloads`、`jobs.manage` 和 `ui.contribute` 必须独立声明、审批和检查。
- `FR-56`：本机 Python、原生二进制、TensorRT engine 构建和任意进程执行只允许内置或通过固定官方信任根验证的签名插件。
- `FR-57`：插件不得通过参数、manifest、权重或路径逃逸访问插件根目录、应用目录、其他插件目录或未授权文件。
- `FR-58`：网络 provider 必须有域名/协议/方法/大小/超时限制；敏感 header 只能由宿主按 credential 引用注入。
- `FR-59`：模型权重和插件包必须记录来源、哈希、许可证和签名状态；签名失效、撤销或哈希变化时禁止运行。
- `FR-60`：任务、日志和预览的生命周期结束后应撤销句柄和临时授权；应用关闭、插件停用和页面销毁必须释放订阅和进程。

### 8.11 自定义组件库与页面样式

- `FR-61`：AI 图像处理页面必须使用 `@guyantools/plugin-ui` 的公开 `gt-*` 组件和 token；页面不得直接依赖 Electron、Node 或宿主 store。
- `FR-62`：组件定制应优先通过 `--gt-*` CSS token，其次使用组件公开的 `::part(...)`，业务布局使用页面 BEM-like class；不得选择 Shadow DOM 私有 class。
- `FR-63`：组件库文档必须给出按钮、卡片、输入、选择器、进度、徽章、滚动条、对话框、插槽、事件和主题切换的定制示例。
- `FR-64`：自定义样式必须覆盖默认、hover、focus-visible、active、disabled、loading、错误和 reduced-motion 状态，并通过对比度检查。
- `FR-65`：左右固定栏、中央滚动区、浮层 body portal 和滚动条不得产生双重滚动或裁切；窄窗口必须有可验证的折叠/抽屉行为。

## 9. 业务规则与数据规则

- `BR-1`：模型能力来自插件 manifest；宿主只负责通用调度和安全边界，不根据模型名称推断能力。
- `BR-2`：`capabilities` 描述业务能力，`permissions` 描述宿主原语；一个 capability 不能隐式增加权限。
- `BR-3`：同一任务的输入、模型版本、后端、精度和关键参数必须可重现；随机生成任务必须保存 seed 或明确标记为随机。
- `BR-4`：当模型、后端、驱动或权重变化导致结果不可复现时，任务详情必须记录变化原因。
- `BR-5`：后端自动选择只能在插件声明兼容且探测成功时执行；手动选择的不可用后端必须阻止提交。
- `BR-6`：同一插件的私有环境、权重缓存和 engine 缓存相互隔离；不得用文件名代替内容哈希作为唯一身份。
- `BR-7`：远程 provider 的密钥归用户所有，任务历史只能保存引用、provider 和模型元数据，不保存密钥。
- `BR-8`：原图永不被处理任务覆盖；输出失败或校验失败时保留原图和临时失败记录，临时文件按清理策略删除。
- `BR-9`：许可证、模型来源和内容安全限制必须在模型详情和导出元数据中可查看。
- `BR-10`：所有时间、大小、费用和性能展示必须标明单位及是否为估算值。

## 10. 非功能需求

### 10.1 性能

- 页面首屏应在插件资源加载完成后 2 秒内呈现可操作的工作台骨架；模型权重和后端探测不得阻塞首屏。
- 运行状态事件默认以不高于 250ms 的 UI 更新频率合并，避免高频日志导致 renderer 卡顿。
- 大图预览应使用缩略图或分块策略，预览缩放不能复制多份完整原图到 renderer。
- 同一任务的内存/显存预算必须在提交前可见；超过插件声明上限时阻止运行或要求用户确认。

### 10.2 可靠性

- 本地进程异常退出、设备丢失和应用重启后，任务记录必须进入可解释的终态或恢复态，不得永久显示“运行中”。
- 任务、缓存和临时文件写入应采用原子更新或可恢复索引，避免半写文件被展示为结果。
- 后端探测和依赖安装必须可重复执行；重复安装不能破坏已可用环境。

### 10.3 安全与隐私

- UI、worker 和宿主边界必须保持沙箱与白名单 API；模型插件不得直接访问 Node/Electron。
- 本机执行与网络访问都必须经过权限、来源和参数校验；进程使用 `shell: false` 等安全启动约束。
- 默认不上传本地图片；远程任务必须显式确认 provider 和数据范围。
- 诊断日志须脱敏，且支持用户删除任务、日志和远程 prompt 元数据。

### 10.4 兼容性

- 首期目标平台为 Windows x64 和 Linux x64，实际后端能力由插件和运行时声明。
- ONNX Runtime、TensorRT、CUDA、驱动、WebGPU adapter、Python 和 PyTorch 版本必须以兼容矩阵管理，不允许只按操作系统判断。
- 插件 UI 必须在 light/dark 主题和键盘操作下保持可用；支持 `prefers-reduced-motion`。

### 10.5 可观测性

- 每个任务、进程、远程请求和后端探测结果都应有可关联 ID。
- 指标至少包括任务数、成功率、取消率、失败分类、耗时、后端使用率、缓存命中率、峰值内存/显存（可获取时）和远程 provider 费用/额度（可获取时）。
- 指标不得包含原图内容、API 密钥或未授权路径。

## 11. 依赖与约束

### 11.1 当前仓库依赖

- `desktop/src/main/plugin-host`：插件生命周期、权限、路由、任务和宿主服务边界。
- `desktop/src/contracts/plugin_model.ts`：当前模型环境、文件句柄和单次推理契约，需要扩展为通用模型任务和后端契约。
- `packages/plugin-sdk/src/contracts.ts` 与 `packages/plugin-sdk/src/runtime.ts`：插件 SDK 和 capability/Job/FileGrant/Network/Secrets API。
- `packages/ui-core` 与 `packages/plugin-ui`：Stencil Custom Elements、Vue/React 适配、公开 token 和 `::part` 契约。
- `desktop/resources/model-plugins/image-enhancement`：当前 Real-CUGAN 内置插件，作为兼容迁移对象。

### 11.2 外部技术调研依据

- **ONNX Runtime Execution Providers**：官方文档列出 CUDA、TensorRT、DirectML、OpenVINO、ROCm、CoreML、WebGPU 等 provider，并将 provider 选择作为推理目标配置。参考：[Execution Providers](https://onnxruntime.ai/docs/execution-providers/)、[TensorRT EP](https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html)、[WebGPU EP](https://onnxruntime.ai/docs/execution-providers/WebGPU-ExecutionProvider.html)，调研日期 2026-10-04。
- **NVIDIA TensorRT**：官方文档将 engine 构建、ONNX 使用、运行时 API、安装方式和支持矩阵分开说明；因此 TensorRT 需求必须包含 engine 生命周期和版本兼容检查。参考：[NVIDIA TensorRT Documentation](https://docs.nvidia.com/deeplearning/tensorrt/latest/)，调研日期 2026-10-04。
- **Hugging Face Diffusers**：官方文档覆盖 DiffusionPipeline、图像生成/编辑、LoRA、量化、硬件加速和部署；因此生成、修复、编辑模型应由插件声明 pipeline 和参数，而不是在宿主创建固定模型列表。参考：[Diffusers Quickstart](https://huggingface.co/docs/diffusers/main/en/quicktour)，调研日期 2026-10-04。
- **WebGPU 标准**：W3C 文档定义 GPU adapter/device、设备丢失和 WebGPU API 生命周期；因此 WebGPU 需要独立的 renderer/worker 运行边界和设备丢失处理。参考：[WebGPU](https://www.w3.org/TR/webgpu/)，调研日期 2026-10-04。
- **第三方图像生成 API**：OpenAI 官方文档将 Images and vision 作为独立 API 能力和生产部署入口；本需求不绑定单一 provider，而要求 provider 插件抽象请求、密钥、结果和费用元数据。参考：[Images and vision](https://platform.openai.com/docs/guides/images)，调研日期 2026-10-04。

### 11.3 约束

- 现有插件运行时的本机模型执行仅向内置或正式信任根签名插件开放；扩展后不得放宽此规则。
- 现有 `models.execute` 语义不能自动覆盖远程网络、密钥或下载权限，新增能力必须独立声明和审批。
- 模型权重、ONNX 文件和 TensorRT engine 不应默认打进桌面安装包；需通过可校验的缓存/下载流程管理。
- 真实模型端到端效果、TensorRT 性能和 WebGPU 跨设备支持必须在具备相应硬件/驱动的机器上单独验证，不能用 TypeScript 构建成功替代。

## 12. 边界场景与失败处理

| 场景 | 系统行为 |
| --- | --- |
| 没有可用模型 | 显示任务类型空状态、安装/导入模型入口和兼容性说明 |
| 没有可用后端 | 显示模型可用后端、探测失败原因和替代模型，不允许提交 |
| 模型权重哈希不匹配 | 阻止加载，删除或隔离文件，提示重新下载/重新导入 |
| TensorRT engine 过期 | 标记缓存失效，保留原 engine 供诊断，并提供可取消重建 |
| ONNX EP 算子不支持 | 显示不支持摘要，允许换 EP 或插件提供 CPU fallback |
| WebGPU adapter 丢失 | 终止当前任务，保存设备丢失错误，允许重试或切换后端 |
| 输入图像过大 | 预估资源，允许用户按插件策略缩放/分块或阻止提交 |
| 输入包含透明通道 | 根据模型声明保留、合成背景或提示不支持；不得静默丢弃 alpha |
| 远程 provider 限流 | 显示 retry-after（若有），按 provider 策略退避，不重复扣费 |
| API key 缺失/失效 | 不发起图片上传，打开 provider 设置或密钥配置入口 |
| 用户中途取消 | 停止可停止阶段，清理临时授权，输出不进入完成列表 |
| 应用重启 | 恢复已持久化任务状态；无法恢复的进程标记为异常终止 |
| 左右栏遮挡中央内容 | 视为布局缺陷；中央滚动区必须保留固定栏安全边距 |
| 插件被停用 | 取消该插件任务、撤销句柄和订阅，历史记录保留为不可重试或可迁移状态 |

## 13. 验收标准

- `AC-1`：假如用户打开工作台，当窗口宽度足够时，则顶部工具栏、左栏和右栏固定，中央区域独立滚动，滚动时三者不随内容移动且不遮挡内容。
- `AC-2`：假如用户选择 Real-CUGAN，当环境、权重和输入满足现有约束时，则 2x/3x/4x、tile、CPU/CUDA、半精度和取消流程保持可用，旧任务记录可查看。
- `AC-3`：假如插件声明 CPU、CUDA 和 TensorRT 三个后端，则页面显示三者的探测结果、版本约束和不可用原因；用户选择 TensorRT 时会校验或构建匹配 engine。
- `AC-4`：假如 ONNX 模型在目标 EP 上存在不支持算子，则任务不会静默降级，页面显示原因并提供可选后端。
- `AC-5`：假如浏览器 GPU 不支持 WebGPU 或设备丢失，则页面显示可操作错误，任务进入终态，可切换本地后端重试。
- `AC-6`：假如插件声明 `restore` 和 `inpaint`，则目录可按任务筛选，参数表单由 schema 生成，遮罩坐标在缩放预览和实际输出中保持一致。
- `AC-7`：假如用户调用远程生成 provider，则发送前能看到 provider、模型、图片/遮罩发送范围和费用信息；缺少确认或密钥时不会上传数据。
- `AC-8`：假如远程请求失败为鉴权、限流或内容政策错误，则错误分类不同，只有可重试错误进入退避重试，密钥不出现在日志中。
- `AC-9`：假如任务运行中关闭应用或停用插件，则本地进程被终止或记录无法终止的原因，文件句柄撤销，历史不显示永久运行中。
- `AC-10`：假如用户删除缓存，则系统按插件/模型/后端列出受影响缓存并删除对应权重或 engine，不删除原图和已完成输出。
- `AC-11`：假如用户使用键盘操作或启用 reduced-motion，则所有核心控件有可见焦点，动效被减少，状态仍有文本/语义表达。
- `AC-12`：假如插件 UI 使用组件库自定义样式，则 token、公开 `::part`、slot 和事件能在 light/dark 主题下生效，且不依赖 Shadow DOM 私有选择器。
- `AC-13`：插件包、模型权重和 engine 哈希或签名异常时，系统拒绝执行并留下可审计原因。
- `AC-14`：在具备目标硬件的 Windows x64 和 Linux x64 环境中，至少完成 Real-CUGAN CPU/CUDA、一个 ONNX Runtime EP、一个 TensorRT 兼容模型和一个 WebGPU smoke test；没有相应硬件时必须记录“未验证”，不能用构建结果替代。

## 14. 假设

- `假设-1`：GuYanTools 继续以 Electron 桌面端为主，插件 UI 使用 sandboxed WebContentsView 和现有 SDK。
- `假设-2`：首个扩展版本优先实现本地模型统一契约和远程 provider 安全边界，模型数量可以分阶段增加。
- `假设-3`：第三方 provider 的具体 API、价格、区域和内容政策会变化，由 provider 插件版本管理，不固化在宿主核心。
- `假设-4`：模型插件可以为不同后端提供不同权重或转换产物；跨后端转换不是宿主自动完成的默认职责。
- `假设-5`：性能目标中的显存、耗时和吞吐需要在目标设备矩阵上校准，文档中的展示要求不等同于已测得的性能承诺。

## 15. 待确认问题

- `Q-1`：首个多模型版本是否必须同时支持批量队列，还是先完成单图、多输入和可扩展协议？
- `Q-2`：远程 provider 首期支持哪些厂商，是否需要统一额度统计或仅显示 provider 返回值？
- `Q-3`：是否允许用户导入任意 ONNX 文件，还是只允许模型插件声明并校验的 ONNX 资产？
- `Q-4`：TensorRT engine 是由插件本地构建，还是由官方插件分发预构建 engine？两者是否都需要？
- `Q-5`：WebGPU 首期是仅用于 ONNX Runtime Web，还是允许插件提供自定义 WGSL/WebGPU pipeline？
- `Q-6`：远程生成的 prompt、参考图和结果是否需要本地加密保存，以及默认保留多久？
- `Q-7`：是否需要输出内容安全审核、隐形水印或生成内容标识？
- `Q-8`：是否需要 GPU 多卡选择、显存隔离和跨任务并发？
- `Q-9`：是否要将视频、动图和批量目录作为同一平台的后续任务类型，还是拆为独立插件？
- `Q-10`：官方签名插件的固定信任根、撤销列表和发布流程由哪个团队维护？

## 16. 建议的后续确认项

1. 先确认统一任务协议和 manifest 字段，尤其是 `task`、输入输出端口、参数 schema、backend、权重和 provenance。
2. 选定一条最小验证矩阵：Real-CUGAN（PyTorch CPU/CUDA）、一个 ONNX 模型（CPU 或 CUDA EP）、一个 TensorRT 模型、一个 WebGPU 模型和一个远程 provider。
3. 在目标 Windows x64/Linux x64 设备上建立后端兼容矩阵，记录驱动、运行时、模型版本、精度、显存、耗时和失败原因。
4. 将现有 `plugin_model.ts` 的单一 `device` 契约升级为通用 backend/任务契约，同时保留 Real-CUGAN 兼容适配。
5. 在实现 UI 前先确定组件库公开的 token、`::part`、slot 和事件合同，并为固定左右栏、中央滚动区和窄窗口折叠写布局验收用例。
6. 把远程 provider 的 secrets、network、费用和隐私确认作为独立安全评审项，不与本地 `models.execute` 一起默认放行。
